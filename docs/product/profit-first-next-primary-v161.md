# V161 · 利润优先的 Merchivra 产品方向与 Next.js 单一前端目标

> **现阶段交付**：更新产品优先级与 Next 页面信息架构，**不是**已经完成全成本净利润、真实 Amazon 接入或生产 Next 切流。业务/税务政策属 G1/DEC-06/07/08 待签署；项目 #104 仍然 NO-GO。

## 1. 产品北极星

**Merchivra 是以可解释真实利润为核心的 Amazon Seller ERP。** 商品、订单、采购、库存、FBA、FBM、广告、费用、结算、银行和运营异常都是为利润核算提供数据及责任闭环的上游模块。

最重要的五个经营问题：

1. 今天/这个月，**每一个站点、店铺、SKU、订单实际赚了多少**？报表采用哪一期、哪个币种、什么计算口径？
2. **哪项费用造成利润下降**？订单退款、销售折扣、平台佣金、FBA/FBM 履约、广告、头程/关税、仓储/长期仓储、赔偿/调整、汇损/银行手续费、可归属运营开销分别多少？
3. 库存批次/历史成本/退货冲回或采购采购费用变动后，历史报表是否可以追溯重算和解释差异？
4. 平台 Finances 与 Settlement、Ads 和手工供应链成本如何归属到 SKU/订单/期间，且不把同一笔费用扣两次？
5. 哪些数值**尚不可计算**，是费用未知、未分摊、跨币种、数据迟到还是对账异常？谁负责补齐？

优先提供经营者可用的**利润瀑布、全成本明细、成本覆盖率与异常列表**，而不是把越来越多的业务模块堆在经营首页。

## 2. P0 全成本利润核算范围（目标，不得冒充已经实现）

先按订单/SKU/店铺/Marketplace/UTC 或获批当地业务期间形成可追溯事实，最终按确认的财务口径输出。不得直接将来自 Orders 的预计销售与 Finances 入账销售相加；Finances 的平台手续费以来源**有符号金额**参与，不能负号重复扣除。

| 分组 | 应覆盖的可核算项目 | 证据与边界 |
| --- | --- | --- |
| 收入和退款 | 商品成交、促销/优惠券、可归属运费收入、退款、跨期退款/调整 | Orders 为运营参考，Finances 为已入账来源；税金是否卖家收入须按市场/税务政策决定 |
| 历史商品成本 | 采购单价、生产/包装、成本生效版本、库存批次、退货 COGS 回转 | 多来源成本归属可复算；历史订单不能直接使用今天的进货价 |
| Amazon 平台费用 | Referral fee、FBA/其他履约、退货处理、仓储/超龄库存、服务费、赔偿和其他调整 | 区分与订单直接相关、SKU 分摊、期间费用；不可重复计入 Settlement 与 Finances |
| 广告 | SP/SB/SD 及真实来源的支出、活动与 SKU 归属、可归因/不可归因余额 | Ads 授权独立于 Seller SP-API；广告归因销售额不再次累加为新收入 |
| 物流/供应链 | 头程运费、进口税/清关、入仓、FBM 运费、国内仓储/尾程等 | 需采购/FBA/承运商真实单据或审查通过的手工证据；合理分摊与未分摊并存 |
| 期间及其他经营费用 | 卖家实际承担的税费、支付/银行手续费、汇损、可分摊固定费用 | 与法定会计/所得税分开，按用户获批政策和费率时点计算 |

建议分别展示（均原币、来源和时间口径明确）：

- **商品毛利** = 业务确认的销售净额 − 已确定商品成本；它不是平台最终贡献。
- **已知费用贡献额** = 已核验销售及相关正负调整 − 历史 COGS − 已分类平台/FBA/其他纳入项；仅在现有 V33/V61/V64 的明确范围下计算。
- **全成本经营利润（目标）** = 合格净销售 − COGS − 所有归属履约/平台/广告/物流/仓储/其他经营费用 ± 已审经营调整；税费归属、汇率、退款回转须 G1 确认。金额完整前必须标识为**待核算**或有明确覆盖率的*部分利润*，不可自动填零。
- **结算/实际到账** 独立对账，不等于利润；期间现金流也不等于贡献利润。

### 数据质量就是利润功能本身

对每一个利润对象，必须有来源链接（事件/报表/订单行/发票/成本版本），原币/计算币、业务与入账日期、覆盖范围、完整度、快照时间、规则版本和重算审计。分摊应满足来源金额守恒，支持不可归属费用池、冲销、差异重审和跨期退款。**UNKNOWN ≠ 0**；多币种不得不经审核汇率直接相加；利润率分母为空或非正时显示“不可计算”，不伪造百分数。

任何“完整净利润”显示条件都必须通过 **全成本覆盖、未分摊余额处理、真实来源完整、汇率/退款政策确认、结算差异解释和独立财务复核**。这些条件未达成时只能显示明示边界的“贡献估算”，不得称法定会计净利润或已对银行账。

## 3. 已实现与缺口（2026-11-14，基于 V160 main）

**已存在可运行的基础**（未验证真实 Amazon）：

- 历史 SKU 成本生效版本与订单 COGS 来源校验（V19/V29）。
- Finances 交易/分类/原币、订单贡献公式、SKU 预览及受审多 SKU 分摊（V33/V61/V62）。
- V64 冻结整期报表和 SKU/订单 CSV，以及经营总览引用最新报告；基础广告人工参考、结算来源导入、部分银行回款对账与异常列表已存在。
- Java BigDecimal/PG18 NUMERIC、Session/Owner/CSRF、CSV/审计与来源状态标记。

**尚未完成的 P0 利润闭环**：

- 广告与 FBA 仓储/头程/FBM/服务费用的**完整来源覆盖、分摊与跨期对账**，真实授权仍关闭。
- 退款退货与批次成本回转的可验证决策，含独立审查和历史版本重算。
- 经批准的费率/汇率/税费/期间规则、分摊方法，严格隔离币种并可追溯。
- 全店铺/SKU/订单可回钻的**全成本利润流水与利润率**，成本覆盖度、缺项责任工单、版本化整期利润报表与自动化差异复核。
- G1 财务/业务签署、真实 Seller/Ads 授权后实际来源比对、G2/G3 目标部署/安全/备份批准。

## 4. 优先级重排（从下一阶段开始）

| 顺序 | 交付 | 可验证验收 |
| --- | --- | --- |
| P0-A | 成本科目字典 + 明细原始来源、币种、业务期、内部 SKU/站点映射和未知状态 | 逐来源不重复计入、同一笔 Finance/Ads/Settlement 重放无重复入账；合成样本下有可追溯缺项 |
| P0-B | FBA/FBM/广告/头程仓储/退款成本分摊与审核队列 | 分摊金额守恒、双人审核/变更后失效、多 SKU/跨期/币种负例 |

| P0-D | Next 利润中心首页 + 整期/按 SKU/订单/站点多维报表和导出 | 从概览到单笔来源钻取、数据不齐显式阻断、CSV/页面/API 一致；站点币种隔离 |
| P0-E | 原始数据对账、冻结/重算差异与正式 G1 财务验收 | 真实目标本地批准后对照 Finances/Settlement/Ads/采购单，正式财务负责人确认口径 |

不再用基础设施小版本升级挤占这些产品 P0。架构/安全测试保持按风险验证，但不能代替财务端到端效果验收。

## 5. 2026 前端技术统一方向

- **正式 ERP 唯一目标：React 19 + Next.js 16 App Router + TypeScript + TanStack Query/表格 + Base UI**，服务端仍是 Spring Boot 4 + Java 25/Gradle + PostgreSQL 18。Orval/OpenAPI 保持唯一 API 客户端契约。
- **Vite 不作为长期并行 ERP 前端**。当前 `deploy/compose.yaml` 的 `web` 默认仍是 Vite 静态构建/Nginx；`deploy/compose.next.yaml` 的 `next-web` 是真实 Next Node runtime，已在隔离 PG18、Chromium、HTTPS Next→Vite→Next 通过技术回归。**这些并不代表正式目标已经换成 Next**。
- 后续通过目标环境的权限/Session/CSRF/安全代理/视觉/业务等价验证及独立授权后，才将默认私有 ERP 入口指向 Next、冻结 Vite 新功能、保留一个短期可回滚的历史构建；完成真实切换验收后删除重复 Vite 业务入口与构建脚本。不要在今天直接删掉唯一经过长期验证的回退方案，也不得因 Next 技术 Issue #63 CLOSED 就宣布真实上线。
- GitHub Pages 是静态无私密的公开演示，不是正式 ERP。是否继续静态展示可采用独立方案，但不应要求生产 ERP 继续依赖 Vite。
