## Scope

The original V52 evidence (PDF/PNG/JPEG BYTEA) stays untouched and private, protected by V129 successful-download audit and V137 production ClamAV. The V138 `erp_lot_proof_file_governance_audit` is append-only at application level, and had an index on `(tenant_id,proof_id,recorded_at DESC,id DESC)`, but no authenticated all-history API. Showing only a recent slice without navigation would hide older Owner approvals. V138 capacity counted raw original payloads, but there was no explicit tenant-specific warning decision. It would be incorrect to invent a single storage quota or to describe original bytes as PostgreSQL disk usage.

## Changes

- **Indexed full audit navigation:** `GET /api/v1/purchasing/lot-proof-governance/{proofId}/history/page?limit=50&cursor=...`, authenticated Owner session, no-store, 1..100 server-side limit (React requests 50), descending `recorded_at,id` stable keyset and one-row lookahead. Cursor binds domain `V140_PROOF_GOV_AUDIT`, actual tenant, proof ID, offset-aware timestamp and UUID. Invalid/foreign/cross-proof/domain cursors reject **HTTP 400** before SQL. Missing file rejects **404**. API returns event IDs, Owner actor UUID, action, rationale and optional retention proposal date, **never original bytes, private filenames, file digest or session credentials**. The system reuses the existing V88 B-tree; no speculative duplicate history index.
- **Opt-in per-tenant advisory alert:** forward-only PG18 Flyway **V89** adds `erp_lot_proof_file_capacity_threshold` (tenant PK, nullable warning threshold and changing Owner) plus append-only threshold-change audit (tenant+actor FK, rationale and time). No default is guessed. An Owner may explicitly `SET` a 1 MiB..1 TiB raw-payload warning line, or `DISABLE` it (audited). Duplicate unchanged settings are rejected; malformed commands and bounds are HTTP 400; mutations must pass existing CSRF and Owner checks and the tenant row lock. An audit insert failure rolls back the configuration transaction.
- **Monitoring endpoints:** `GET .../capacity-alert` gives `UNCONFIGURED`, `NORMAL`, or `WARNING` based on **SUM(size_bytes) and an explicit configured threshold**, plus raw file count, raw original byte sum and `advisoryOnly=true`. At and above the threshold is `WARNING`. The old V138 `GET .../capacity` still returns legal-hold and retention counts. Both return HTTP 200 no-store when authorized; errors must not be represented as healthy. The API uses the original file's metadata, not `BYTEA` contents.
- **React Owner workbench:** scoped audit-page controls (previous/next, 50 per page with a warning that a page is not a total), reason/actor/date, manual-refresh capacity status and opt-in threshold input/disable flow with a 10..500-character audit rationale. TanStack Query keys include tenant/proof/cursor; cursor navigation resets on proof or tenant change, with Zod guards for malformed/contradictory responses. No automatic emailing, unattended background polling, purge workers, file deletion buttons, or Amazon actions.

## Limitations and production release gate

This feature is **manual, advisory and original-payload-only**. It does **not** measure PostgreSQL physical capacity (TOAST, indexes, free space, WAL, replicas), database backups or point-in-time history. It is not an automatic operational alerting channel (email/SMS/Slack), retention law, a configured quota, an SLA or a denial-of-upload mechanism. Operations must install disk/database/PITR backup monitors and on-call routing independently; do not interpret `NORMAL` as the actual server being healthy. Live tenants need approved thresholds, legal records retention/holds jurisdiction rules, isolated real ClamAV signatures/down tests, audited and encrypted target DB/backups, HTTPS/IAM/rollback/restore rehearsals, and manual G1–G3 signoff before production. No legal hold, `REVIEWED_NO_DELETE` state or threshold can be used to authorize deletion; **no original-file DELETE route or purge exists**.
